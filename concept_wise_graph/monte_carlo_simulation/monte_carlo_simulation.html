Rule typeRule
E folk-meaning ruleFolk meaning: in everyday speech a 70% chance or a single experiment 'tells what will happen', and 'random' means unpredictable and never repeating. A Monte Carlo program gives only an estimate (successes / trials) whose accuracy grows with the number of trials, and Math.random() is pseudo-random, not truly random.
M wrong rule / right ruleFewTrialsAreExact: wrong: A short simulation gives the exact page ranks (or probabilities). | right: A simulation only estimates: RandomSurfer needs 10^n moves for n-decimal precision and many more for accuracy (tens of thousands of moves for two places, millions for three).
M wrong rule / right ruleProbabilityIsPrediction: wrong: A probability (e.g. 70%) predicts what the next single trial will do. | right: A probability is the long-run fraction of successes over many trials. A simulation estimates it as count / trials, and one trial can come out either way.
T uneven-application ruleApplies the LT rule (run a trial, update the counters, repeat T times, divide at the end) unevenly: resets the per-trial state (cash = stake) only once rather than once per trial, or divides inside the loop, so the traced estimate mixes trials.
N identity ruleSimulation technique: estimating a probability or expected value by repeating many independent random trials with Math.random() and averaging the outcomes.
S declarative ruleRun T independent trials in an outer loop, each starting from fresh state; count successes (and accumulate costs). Report `successes / T` (and `total / T`) as the estimates.
LT operational sequencing ruleOrder: initialise the counters once; then, for each trial, reset the trial state, run the inner random process to its end (`while (cash > 0 && cash < goal)`), and update the counters; divide and print only after all T trials.
OP evaluation / result ruleThe output is an estimate that varies from run to run and gets close to the true value as T grows. Gambler 10 20 1000 prints about 50% wins and about 100 bets, close to the theory: stake/goal and stake × (goal − stake).
OS state-transition ruleOne trial resets its own state (cash = stake), consumes random numbers and changes only the summary counters: wins goes up by 0 or 1, and bets goes up by the number of bets made in that trial.
R composition rule (with a neighbour)with math_random: Each random event is driven by Math.random(), which returns a double in [0, 1). An event of probability p is simulated as `Math.random() < p`, e.g. `< 0.5` for a fair bet.
R composition rule (with a neighbour)with counter_pattern: Successes are tallied by a counter declared before the trial loop and incremented once per successful trial. The estimate is that counter divided by T, computed as a double or as `100*wins/T` for a whole-number percentage.
P plan / role rulePlan: simulate-and-count (Monte Carlo). It answers questions that are hard to solve analytically, and it checks analytic results. Roles: trial index = stepper, wins = counter, bets = gatherer.
C conservation ruleIncreasing T keeps the expected estimate and narrows its spread (about 10^n trials per decimal digit), but raises running time in proportion to T. Changing the success test or probability changes what is estimated. Re-running with the same T gives a slightly different number.
D error rulerule broken: Each trial must start from fresh state. (silent logic error)
D error rulerule broken: Estimates from few trials are unreliable. (silent logic error)
D error rulerule broken: Integer division truncates the estimate. (silent logic error)
D error rulerule broken: Running time grows with T times the length of each trial. (silent logic error)
X applicability ruleUse Monte Carlo when an answer is a probability or average of a random process that is hard to analyse (gambler's ruin with a bet limit, Monty Hall, random walks, page ranks). Avoid it when an exact formula or deterministic computation exists and is cheap, or when you need more accuracy than the trial budget can give.

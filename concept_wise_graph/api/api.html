Rules of the concept (13)

Book (SW-1e, p. 29 (pdf 39)): “Such a table is known as an application programming interface (API ).”
Book (SW-1e, p. 29 (pdf 39)): “It provides the information that you need to write an application program that uses the methods.”
Rule typeRule
E folk-meaning ruleFolk meaning: an 'interface' is a screen you click on, and documentation shows the code you type. SW rule: an API is a table of library methods, each line giving the method's signature (return type, name, argument types) and what it computes; the signature is not the code you type to call it.
T uneven-application rulePoints to LT (read an entry as return type, then name, then argument types in order, and write the call to match). Applied unevenly: the student matches the name and arguments of Math.round but ignores its return type (int n = Math.round(x)), or copies the parameter types into the call on some lines.
N identity ruleAn API (application programming interface) is a table of library methods giving, for each, its signature and a short description of what it computes.
S declarative ruleEach API line specifies the return type, the method name and the types of its arguments (the signature), plus a description; it provides the information needed to write a program that uses the method.
LT operational sequencing ruleTo use an entry: find the method, read its signature left to right (return type, name, parameter types in order), write a call with the name and argument expressions of those types in that order, and use the returned value according to the return type (none for void).
OP evaluation / result ruleFrom the API alone one predicts the type of a call's value: Math.sqrt returns a double, Math.round a long, Integer.parseInt an int, println nothing (void).
OS state-transition ruleReading the API changes nothing in the program; it states what each call returns, and (for void methods such as println) what effect the call has instead of a value.
R composition rule (with a neighbour)with method_call: Each call must match one API signature: same name, arguments of the listed types in the listed order, and use of the value consistent with the return type.
P plan / role ruleAn API is a contract that separates the client, who needs only the signatures and descriptions, from the implementation; it lets programmers use large libraries without reading their code, and later to design their own libraries.
C conservation ruleClient code keeps working when a method's implementation changes but its signature and behaviour stay the same; changing a signature (name, parameter types, return type) breaks every call that relies on it. Choosing which methods an API includes is a trade-off between convenience and size.
D error rulerule broken: A call must match the API signature (argument types/number/order and return type). (compile-time)
D error rulerule broken: The API describes what the method returns; a value-returning call does not change its arguments. (silent logic error)
X applicability ruleConsult the API whenever you use a library method (to get name, argument order and return type right); if no listed method fits, combine listed ones (e.g. secant from Math.cos) or write your own.

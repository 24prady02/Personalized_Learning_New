Rules of the concept (25)

Book (SW-1e, p. 46 (pdf 56)): “each of the statements in the program is executed once, in the order given.”
Book (SW-1e, p. 70 (pdf 80)): “The if and if-else statements allow one or two alternatives in directing the flow of control.”
Book (OT-Expressions, ): “Finally, control flow statements regulate the order in which statements get executed.”
Rule typeRule
E folk-meaning ruleFolk meaning: in everyday instructions a listener reads the whole list at once, does steps in a sensible order and infers what the writer wants. Java instead executes statements one at a time, top to bottom, each only when control reaches it, and nothing later in the program has any effect earlier.
M wrong rule / right ruleCodeAfterIfSkipped: wrong: When the then branch runs, the code after the if is skipped. | right: After the if finishes, execution continues with the next statement either way.
M wrong rule / right ruleNoShortCircuit: wrong: logical AND/OR always evaluate both sides (Java short-circuits them) | right: In p && q, q is evaluated only when p is true; in p || q, q is evaluated only when p is false.
M wrong rule / right ruleStatementsRunInAnyOrder: wrong: Statements in a program can run in any order. | right: Without control statements, statements run once each, top to bottom.
M wrong rule / right ruleLoopImpliedByOneTest: wrong: Testing one case is enough; Java will repeat the test for the other values by itself. | right: A statement runs once each time control reaches it; repeating a test for many values needs a loop.
M wrong rule / right ruleIfWaitsForCondition: wrong: An IF statement earlier in the program stays active and fires later, e.g. inside a later loop, when its condition becomes true. | right: An if is evaluated once when control reaches it; afterwards it is inactive unless control returns to it.
M wrong rule / right ruleProgramLooksAhead: wrong: The program knows or sees what later lines will do and acts on those goals at the current line, e.g. it stops 'at ten' because it wants to draw a box. | right: Each statement executes using only the current state; later lines have no effect until control reaches them.
M wrong rule / right ruleFalseConditionRestartsProgram: wrong: When an if condition is false (and there is no else), control jumps back to the start of the program. | right: A false condition skips the then branch and execution continues with the statement after the if statement.
M wrong rule / right ruleIfConditionWatched: wrong: An if statement watches its condition while the program runs and fires as soon as the condition becomes true (if = whenever). | right: An if condition is tested once, when control reaches the if statement; later changes to the variables do not trigger the branch.
M wrong rule / right ruleProgramEndsAfterLoop: wrong: When a loop finishes the program ends, so code after the loop never runs. | right: When the loop condition becomes false, control continues with the first statement after the loop.
M wrong rule / right ruleFalseLoopRepeatsNextCode: wrong: A loop is an iterative if-else: while the condition is true the body repeats, and when it is false the code after the loop repeats. | right: Only the body is repeated; once the condition is false the code after the loop runs once.
T uneven-application ruleApplies the sequencing rule (LT) unevenly: e.g. runs a later line before an earlier one, lets an if that was already passed fire again later, or ends the program when a loop or a false if ends instead of continuing with the next statement.
N identity ruleControl flow is the order in which a program's statements are executed (statement sequencing); conditionals and loops are the statements that change it.
S declarative ruleWithout control statements every statement executes once, in the order given; a block executes its statements in order from first to last; if/if-else choose between one or two alternatives and loops repeat statements depending on a condition.
LT operational sequencing ruleExecute the statement at the current point; when it completes normally, control passes to the next statement in the block. An if evaluates its condition once and then runs at most one branch; a loop evaluates its condition before each pass; after an if or a loop finishes, control continues with the statement after it.
OP evaluation / result ruleThe output is the sequence of print statements that control actually reaches, in the order reached: e.g. TenHellos prints 1st, 2nd, 3rd Hello once each, then 4th to 10th Hello from the loop.
OS state-transition ruleOne step executes the single statement at the current control point using the current values, updates at most the variables it assigns, and moves the control point to the next statement (or, for an if/loop test, to the chosen branch, back to the test, or past the statement).
R composition rule (with a neighbour)with statement: Control flow is defined over statements: statements are executed for their effect, and if/while/for are themselves statements that may be used wherever a statement is allowed, so they can nest.
R composition rule (with a neighbour)with if_statement: An if changes the default top-to-bottom flow: its condition is tested once when control reaches it, its block runs only if true, and in both cases control then continues with the next statement.
R composition rule (with a neighbour)with flowchart: A flowchart draws control flow: each path through the diagram is a possible path of execution, with a decision box for each if or loop test.
P plan / role rulePlan: control flow lets one program do different things for different inputs (selection) and do a thing many times (repetition), so a short program can specify a potentially unlimited number of executed statements.
C conservation ruleReordering two statements generally changes the result whenever one reads a variable that the other writes (e.g. swapping x = x + 1 and print(x)); reordering is safe only for statements that touch disjoint variables. Moving a statement into or out of a branch or loop body changes how many times it runs (0, 1 or n).
D error rulerule broken: A local variable must be definitely assigned on every control-flow path before it is read. (compile-time)
D error rulerule broken: Statements run in the order written, so an update must come before the statement that needs the new value. (silent logic error)
X applicability ruleReason in terms of control flow whenever you must predict output or find why a statement did or did not run: trace which statement is reached next. Straight-line sequence suffices only when every input needs the same steps exactly once; otherwise add a conditional or a loop.

  • [7] misconception (M) → IfWaitsForCondition: wrong rule: An IF statement earlier in the program stays active and fires later, e.g. inside a later loop, when its condition becomes true. Right rule: An if is evaluated once when control reaches it; afterwards it is inactive unless control returns to it.
  • [8] misconception (M) → FalseConditionRestartsProgram: wrong rule: When an if condition is false (and there is no else), control jumps back to the start of the program. Right rule: A false condition skips the then branch and execution continues with the statement after the if statement.
  • [9] misconception (M) → IfConditionWatched: wrong rule: An if statement watches its condition while the program runs and fires as soon as the condition becomes true (if = whenever). Right rule: An if condition is tested once, when control reaches the if statement; later changes to the variables do not trigger the branch.
  • [10] misconception (M) → ProgramEndsAfterLoop: wrong rule: When a loop finishes the program ends, so code after the loop never runs. Right rule: When the loop condition becomes false, control continues with the first statement after the loop.
  • [11] misconception (M) → FalseLoopRepeatsNextCode: wrong rule: A loop is an iterative if-else: while the condition is true the body repeats, and when it is false the code after the loop repeats. Right rule: Only the body is repeated; once the condition is false the code after the loop runs once.

Rules of the concept (16)

Book (SW-1e, p. 73 (pdf 83)): “For each exercise, you will write a Java program, then run and test it.”
Book (SW-1e, p. 177 (pdf 187)): “each one is the product of a long bout of testing, fixing bugs, and running the programs on numerous inputs.”
Book (TJ-2e, p. 165 (pdf 187)): “Test your method with multiple strings, including some that are balanced and some that are not.”
Rule typeRule
E folk-meaning ruleEveryday 'test' means trying something once to see whether it works. A program test runs the program on several chosen inputs, each with an expected output worked out in advance, and compares the two.
M wrong rule / right ruleOneTestProvesCorrect: wrong: If a program gives the right output for one input, it is correct. | right: One passing run shows only that this input works; check the program on numerous inputs, including boundary and unusual ones.
M wrong rule / right ruleCompilesMeansWorks: wrong: Code that compiles is code that works. | right: Compiling checks only the form of the code; whether it does the right thing is found by running and testing it.
T uneven-application ruleApplies the testing rule unevenly: checks the output for one input against an expected value, but accepts the output for another input without working out what it should be.
N identity ruleTesting: running the program on chosen inputs and comparing each output with the expected output.
S declarative ruleWrite the program, then run and test it: choose inputs, work out the expected output of each in advance, run the program on each, and compare. Include the boundary cases (0, 1, the largest value, an empty input).
LT operational sequencing ruleSequencing: first decide the inputs and expected outputs, then run the program once per input, then compare each output with its expectation; a mismatch is recorded before anything is changed.
OP evaluation / result ruleResult: for each input the test gives pass (output equals expectation) or fail; the program is accepted only when every chosen input passes.
OS state-transition ruleState transition: one test run leaves the program unchanged and adds one pass or fail to what is known about it.
R composition rule (with a neighbour)with run: Each test is one run with one input: java Name followed by the test arguments (or with input redirected from a file).
R composition rule (with a neighbour)with program_trace: The expected output of a test comes from a hand trace of what the program should do for that input.
R composition rule (with a neighbour)with debugging: A failing test starts debugging; after the fix, the same test is run again to confirm it.
P plan / role rulePlan: tests give evidence that a program does what it should for the inputs that matter, and catch the cases where it does not.
C conservation ruleConservation: after any change to the program, the earlier tests must still pass; a fix for one input that breaks another is caught by re-running them all.
D error rulerule broken: A program is checked on several inputs, including the boundary cases. (silent logic error)
X applicability ruleTest every program you write, before using its output: on the given example, on the boundary values, and on an input whose answer you can work out by hand.

Rules of the concept (13)

Book (SW-1e, p. 111 (pdf 121)): “The state of a program can be defined as the information you need to know to understand what a program is doing.”
Rule typeRule
E folk-meaning ruleFolk meaning: program statements read like maths equations, timeless relations among values. Java rule: each statement changes the state (the values of variables and array entries), and the next statement starts from the changed state.
M wrong rule / right ruleStateChangeIgnoredAcrossPasses: wrong: Values changed by one pass of a loop (other than the loop variable) do not affect later passes. | right: Each pass starts from the state left by the previous pass, so a change in one pass carries into the next ones.
T uneven-application rulePoints to LT: statements execute one at a time, and each starts from the state the previous one left. Inconsistent application: a trace table updates a variable on some steps but carries a stale value on others.
N identity ruleIdentity: the state of a program is the information needed to know what it will do next: the values of its variables (and array entries) and which statement runs next.
S declarative ruleDeclarative: in a program without arrays, knowing the variable values and the next statement determines what the program does next; arrays add one state component per element.
LT operational sequencing ruleSequencing: statements in a block execute in order, first to last, so the state seen by each statement is the result of all earlier ones.
OP evaluation / result ruleResult: the output from any point on is determined by the current state; equal states give the same future behaviour (apart from Math.random and input).
OS state-transition ruleState transition: each assignment changes exactly one variable or one array element; tracing tracks these changes.
R composition rule (with a neighbour)with variable: Without arrays the state is the values of the variables plus the next statement; each array element adds one more variable to the state.
P plan / role rulePlan/role: tracing (a trace table of the state after each step) is how programs are understood and debugged; with large arrays one checks invariants among state components instead.
C conservation ruleConservation: an invariant such as 'valcnt equals the number of true entries in found[]' holds after every pass; a change that breaks it signals a bug.
D error rulerule broken: Each pass starts from the state left by the previous one. (silent logic error)
X applicability ruleApplicability: trace the full state for small programs. When arrays make the state too large to track, reason with invariants and partial traces instead.

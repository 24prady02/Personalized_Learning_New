Rule typeRule
E folk-meaning ruleFolk meaning: in everyday instructions ('lather, rinse, repeat', 'while the road is two lanes, continue north') the reader stops sensibly or watches the condition all the time. A Java loop repeats only while its condition is true at each test, and it never stops on its own if no pass makes the condition false.
M wrong rule / right ruleCompoundAssignmentNoCast: wrong: `x += 0.5` adds one half to an int x. | right: `x += 0.5` means `x = (int) (x + 0.5)`; the narrowing rounds toward zero, so a nonnegative int x keeps its value, and a loop relying on it never progresses.
M wrong rule / right ruleInfiniteLoopUnnoticed: wrong: A loop whose condition never goes false will still terminate. | right: A while loop stops only when its condition is false at a check, so if no pass changes the variables in the condition, it never stops.
M wrong rule / right ruleJavaDetectsInfiniteLoops: wrong: If my loop never ends, the compiler or Java will warn me. | right: Java cannot detect infinite loops in general (the halting problem); you must check that the condition eventually becomes false.
M wrong rule / right ruleLoopVariableNotUpdated: wrong: A while loop ends by itself even if nothing in the body changes the variable tested in the condition. | right: If no statement in the body changes a variable in the condition, a condition that was true stays true and the loop never ends.
T uneven-application ruleApplies the loop LT rule unevenly: on a trace, the update is assumed to happen on every pass even when it is skipped (e.g. by continue or inside an if), or the loop is assumed to stop when the condition becomes false in the middle of the body. The traced run then ends where the real one does not.
N identity ruleLoop bug/behaviour: a loop whose continuation condition never becomes false, so it runs until the program is killed (or overflow intervenes).
S declarative ruleA while or for loop terminates only if some pass makes its condition false at a test (or a break or return runs). Otherwise it repeats forever. The compiler does not check this.
LT operational sequencing ruleThe same order as any loop: test, body, test... In an infinite loop the update either never runs or never moves the tested variables towards false, so every test yields true.
OP evaluation / result ruleThere is no final value. Either output scrolls forever (BadHellos with `i > 3`) or nothing happens and the program 'hangs'. Over a very long run, int overflow may eventually make the test false (BadHellos stops after about 2^31 lines).
OS state-transition ruleEach pass leaves the condition's variables either unchanged or moving away from false (i grows while the test is `i > 3`). So the state after the pass satisfies the condition again.
R composition rule (with a neighbour)with loop_control: A loop is finite only if its update moves the control variable towards making the condition false. Wrong direction (`i--` with `i < n`), wrong step (`i += 0` or `x += 0.5` on an int), or a condition that the update can step over (`i != 10` with `i += 3`) all give infinite loops.
P plan / role rulePurpose: usually a bug. An intentional `while (true)` with an internal break or return is the 'loop-and-a-half' plan for servers, event loops and read-until-sentinel input.
C conservation ruleChanging the condition or update can turn a terminating loop into an infinite one (`i <= 10` to `i > 3`), or the reverse. The termination argument (a quantity that strictly moves towards the bound on every pass) must survive any change.
D error rulerule broken: The body must change a variable in the condition so that it eventually becomes false. (silent logic error)
D error rulerule broken: An empty statement after the loop header becomes the body. (silent logic error)
D error rulerule broken: Tests on doubles or on exact values can be stepped over. (silent logic error)
D error rulerule broken: int arithmetic wraps without warning. (silent logic error)
D error rulerule broken: Code after a loop that can never complete normally is unreachable. (compile-time)
X applicability ruleWrite `while (true)` only when the exit is in the middle of the body and is certain (break or return on a sentinel or event). Otherwise, for each loop, state why the condition eventually becomes false. When a program seems stuck, add trace prints to tell an infinite loop from a slow one.

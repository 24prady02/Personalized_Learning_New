Rules of the concept (14)

Book (SW-1e, p. 24 (pdf 34)): “When working with floating point numbers, one of the first things that you will encounter is the issue of precision: 5.0/2.0 is 2.5 but 5.0/3.0 is 1.6666666666666667.”
Book (SW-1.2, ): “The double type is for representing floating-point numbers, e.g., for use in scientific applications.”
Book (HO, ): “To avoid roundoff errors, don't use == to compare floating-point numbers.”
Rule typeRule
E folk-meaning ruleFolk meaning: decimal arithmetic is exact, as on paper or on a calculator display, so 0.1 + 0.1 + 0.1 equals 0.3. Java rule: most decimal fractions (0.1) have no exact binary representation, every double operation rounds, and (0.1 + 0.1 + 0.1 == 0.3) is false.
M wrong rule / right ruleFloatingPointIsExact: wrong: Math.sqrt(2) * Math.sqrt(2) == 2 is true. | right: A double is an approximation, so the product is 2.0000000000000004, close to 2 but not equal; the comparison is false.
T uneven-application rulePoints to LT (rounding happens after every single operation, and the error is carried into the next one). Applied unevenly: the student rounds only the final printed value, treating intermediate values as exact on some lines, or expects ten additions of 0.1 to equal 0.1 * 10.
N identity ruleFloating-point precision is a property of the double type: a double keeps only about 15 significant decimal digits, and the difference between the intended real number and the stored double is rounding error.
S declarative ruleEach double result is the nearest representable binary64 value, so results are generally approximate; S&W: novice programmers should avoid comparing two floating-point numbers for equality. Do not test doubles for equality with ==: compare with a tolerance, e.g. Math.abs(x - y) < 1e-9; and == is false whenever an operand is NaN.
LT operational sequencing ruleEvaluation proceeds operator by operator; after each one the exact result is rounded to a double, and the next operator works on that rounded value, so errors compound along the evaluation order; only at output is the stored value converted to a decimal string.
OP evaluation / result rulePrinted results show the approximation: 0.1 * 10 prints 1.0 but adding 0.1 ten times prints 0.9999999999999999; 5.0/3.0 prints 1.6666666666666667; (0.1 + 0.1 + 0.1 == 0.3) is false.
OS state-transition ruleEach assignment such as x = x + 0.1 stores the rounded sum; the error stays in x and is carried into every later step that uses x.
R composition rule (with a neighbour)with double: Imprecision is inherent in the double type, not in a particular program: any arithmetic on doubles may carry rounding error, so code that uses double must be written to tolerate it.
R composition rule (with a neighbour)with convergence_test: Because doubles are approximate, a loop that waits for exact equality may never stop; Sqrt therefore loops while Math.abs(t - c/t) > epsilon * t, a relative-tolerance test.
P plan / role ruleAwareness of precision is used to write tolerance comparisons (Math.abs(a - b) < epsilon) and to choose integer representations for exact quantities, e.g. money as an int number of cents.
C conservation ruleReordering additions, or changing a loop step such as x += 0.1, changes the last digits and can change how many times a loop tested with <= runs; replacing an == test by a tolerance test makes the outcome stable under such changes.
D error rulerule broken: Computed doubles must not be compared for exact equality. (silent logic error)
X applicability ruleAccept double precision for measurements and simulations and compare with a tolerance; when exactness is required (counts, money, loop control) use int or long instead.

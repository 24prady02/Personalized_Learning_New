reading_error_messages (id reading_error_messages, section 1.1 Your First Program, topic 1.1.c Errors)

Rules of the concept (17)

Book (SW-1e, p. 11 (pdf 21)): “But the compiler may not be able to tell you exactly what mistake you made, so the error message may be hard to understand.”
Book (RS, ): “A good rule of thumb to follow is that the first error reported by the compiler is the most important one to pay attention to. The rest might be the result of that first error.”
Rule typeRule
E folk-meaning ruleEveryday reading: an error message is like a teacher's correction, naming the exact mistake, its line and its fix, one message per mistake. Java rule: the message reports what javac detected and where it noticed it; one fault can cause several messages and the suggested remedy may be wrong.
M wrong rule / right ruleErrorLineIsFaultLine: wrong: The line number in a javac error is always the line that has the mistake. | right: The compiler reports where it noticed the problem, which can be after the real fault.
M wrong rule / right ruleFixEveryErrorMessage: wrong: Each error message is a separate mistake that needs its own fix. | right: One fault can produce several messages; fix the first and recompile.
M wrong rule / right ruleCompilerSuggestionIsFix: wrong: Doing exactly what the compiler message suggests will fix the error. | right: An error message is evidence that something is wrong, but its suggested remedy may be wrong; find the actual cause.
T uneven-application ruleApplies the read-first-error rule unevenly: starts from the first message on one compile but from the last on another, or looks only at the reported line without checking the lines before it.
N identity ruleReading error messages is the debugging skill of interpreting a compiler (or JVM) message, File.java:line: description, to locate and fix the fault.
S declarative ruleEach javac message gives the file, the line where the error was detected and a description; only the first message is truly reliable, and the real error is generally at or before the reported line.
LT operational sequencing ruleRead the first message, go to its line, look there and then backwards for the cause, fix that one error, recompile, and repeat.
OP evaluation / result ruleReading 'Bad.java:2: '{' expected' yields the location (file Bad.java, line 2) and the kind of problem (a missing left brace); with a later or vaguer message, it yields only where to start looking.
OS state-transition ruleOne read-fix-recompile cycle removes one fault and often several messages; the message count after recompiling can drop sharply.
R composition rule (with a neighbour)with compile_time_error: Compile-time errors are found and fixed by reading their messages; the message maps imperfectly to the fault.
P plan / role rulePurpose: use the compiler as a friend that says something is wrong, turning its message into a hypothesis about the fault.
C conservation ruleIntroducing a known mistake into a working program and reading the resulting message shows which messages a fault produces; adding a fault earlier in the file can change messages reported later.
D error rulerule broken: Reported line = where javac noticed the problem (compile-time)
D error rulerule broken: Suggested remedies are unreliable (compile-time)
D error rulerule broken: Run-time messages name the exception and the line (run-time exception)
X applicability ruleRead messages first-error-first whenever javac or the JVM reports an error; for logic errors there is no message, so use tracing and print statements instead.

  • [1] relation_to_neighbour (R): Reading an error message tells you where to start looking; debugging goes on from there to the cause.
  • [2] purpose_of_the_whole (P): Purpose: use the compiler as a friend that says something is wrong, turning its message into a hypothesis about the fault.
L4Extended abstract (concrete-operational reversibility and conservation)
L4 for reading error messages: the answer reasons beyond the given code by these rules.
Does the answer link the code to a broader context: a changed program, a class of inputs, an unseen problem? Re-tracing changed code value by value is L2; fixing one given failing case is L3.
  • [0] predict_a_change (C) → ErrorLineIsFaultLine: Introducing a known mistake into a working program and reading the resulting message shows which messages a fault produces; adding a fault earlier in the file can change messages reported later.
  • [1] transfer_to_a_new_program (X): Read messages first-error-first whenever javac or the JVM reports an error; for logic errors there is no message, so use tracing and print statements instead.
  • [2] diagnose_an_error (D): rule broken: Reported line = where javac noticed the problem. Kind: compile-time. Trigger class: a missing brace or quote, reported lines later (e.g. reached end of file while parsing)
  • [3] diagnose_an_error (D): rule broken: Suggested remedies are unreliable. Kind: compile-time. Trigger class: a message whose literal advice (e.g. declare a class abstract) is wrong
  • [4] diagnose_an_error (D): rule broken: Run-time messages name the exception and the line. Kind: run-time exception. Trigger class: reading Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: 0 at UseArgument.main(UseArgument.java:6)
